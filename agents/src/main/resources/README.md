# Документация Backstage для агентов

Этот документ поставляется в `com.backstage:agents` и предназначен для работы с приложением, которое подключает библиотеки `com.backstage`. Репозиторий приложения имеет собственные инструкции, структуру и команды проверки; учитывай их при использовании этой документации.

## Выбор материалов по задаче

| Область задачи | Что открыть |
| --- | --- |
| Справочники `dicts`, `dicts-api`, `dicts-codegen` | Skill [backstage-dicts](skills/backstage-dicts/SKILL.md), затем выбранный им справочник |
| Остальные компоненты Backstage | Нужный раздел [COMPONENTS.md](COMPONENTS.md) |
| Поиск реализации в исходниках компонентов | [CODEMAP.md](CODEMAP.md) |

Читай только материалы, относящиеся к текущей задаче. Справочники skill загружаются по необходимости; полную карту проекта и описание всех модулей перед каждой задачей читать не требуется.

Определи подключённую версию Backstage и локальный/remote сценарий приложения. Перед вызовом API проверь контракт этой версии и условия активации. Исходники, упомянутые в справочниках, относятся к репозиторию компонентов; при необходимости используй соответствующий sources JAR. Проверяй изменения командами и тестами приложения.

## Подключение в приложении

Если `com.backstage:gradle-plugins` уже находится в buildscript classpath, добавь плагин в `build.gradle` проекта приложения, в котором объявлены его зависимости.

```groovy
apply plugin: 'backstage-agent-docs'
```

Иначе подключи его так же, как другие Backstage-плагины:

```groovy
buildscript {
	repositories {
		// Maven-репозиторий Backstage и способ авторизации из настроек приложения.
	}

	dependencies {
		classpath "com.backstage:gradle-plugins:$backstageVersion"
	}
}

apply plugin: 'backstage-agent-docs'
```

Maven-репозиторий Backstage должен быть доступен также в обычном `repositories` проекта: buildscript repositories используются только для загрузки самого плагина. Настрой авторизацию тем же способом, что и для остальных компонентов.

После подключения плагина перезагрузи Gradle-проект в IDE. Плагин установит документацию на фазе конфигурации, после обработки `build.gradle`. Это также происходит при запуске любой команды Gradle, включая `help`.

Плагин извлекает базовую документацию из отдельной конфигурации `agentDocs`. По умолчанию `README.md`, `COMPONENTS.md` и `CODEMAP.md` попадают в `.agents/backstage/` в корне сборки, включая применение плагина в подпроекте. В корневом `AGENTS.md` появляется ссылка на документацию.

Каждый skill устанавливается один раз в `.agents/skills/<имя-skill>` в корне приложения. Для `dicts` это `.agents/skills/backstage-dicts/SKILL.md` и его справочники. Агент с поддержкой такого расположения может выбрать skill по имени и описанию. К skill можно перейти и по ссылкам из документации.

При наличии корневого `.gitignore` плагин добавляет в него `/.agents/`, если правила для этого каталога ещё нет.

Плагин обновляет и удаляет только каталоги skills со своим маркером `.backstage-agent-docs`. Остальные skills сохраняются. Если имя совпало с существующим пользовательским skill без маркера, конфигурация завершается ошибкой, сохраняя его файлы. Пользовательские дополнения размещай в собственном skill: содержимое управляемого каталога обновляется вместе с артефактом.

Для базового JAR плагин проверяет `agentDocs.version`, затем Gradle property `backstageVersion` и версию Backstage, встроенную в используемый `gradle-plugins`. Для автоматического обновления используй общее свойство `backstageVersion` из `gradle.properties` для библиотек и плагинов приложения. При его смене следующий импорт или запуск Gradle загрузит документацию той же версии и удалит устаревшие файлы.

Отдельно указывать `agentDocs.version` не нужно. Фиксированное значение этого параметра переопределяет следование `backstageVersion`; используй его только для явного выбора другой версии документации.

При необходимости настрой extension:

```groovy
agentDocs {
	outputDirectory = rootProject.layout.projectDirectory.dir('.gradle/custom-agent-docs')
}
```

Выбери новый или пустой каталог вне `build`. Плагин помечает его файлом `.backstage-agent-docs` и удаляет из него устаревшие материалы при обновлении. При переходе на стандартный путь `.agents/backstage/` плагин удаляет прежние каталоги `.gradle/backstage/agent-docs/` со своим маркером в корне сборки и в проекте приложения. Стандартный путь сохраняет документацию после `clean`.

Артефакт должен быть доступен на фазе конфигурации. Плагин ищет `README.md` в корне JAR и поддерживает `index.md` из старых артефактов. При отсутствии обоих файлов конфигурация завершается до записи документации. Для локальной разработки можно явно задать уже собранный JAR вместо зависимости по умолчанию:

```groovy
dependencies {
	agentDocs files('path/to/agents.jar')
}
```

## Документация в JAR библиотеки

Чтобы поставлять материалы вместе с библиотекой, помести их в `src/main/resources/META-INF/backstage/agents/`. Например, опубликованный JAR `bot-sdk` может содержать такую структуру.

```text
META-INF/backstage/agents/
├── README.md
└── skills/
    └── bot-sdk/
        ├── SKILL.md
        └── references/
            └── handlers.md
```

Для каждого skill нужен `SKILL.md` с именем и описанием. Выбирай уникальные имена на основе названия библиотеки, например `bot-sdk` или `bot-sdk-testing`. `README.md` библиотеки опционален. Ссылки на справочники и файлы внутри skill задавай относительными путями.

В приложении достаточно обычной зависимости на библиотеку и плагина `backstage-agent-docs`. Он ищет ресурсы в опубликованных JAR основного `runtimeClasspath`, включая транзитивные зависимости. Gradle разрешает этот classpath при конфигурации. Пакет документации берётся из выбранной версии JAR и обновляется или удаляется при изменении зависимости. Для встраиваемых материалов используются опубликованные артефакты Maven, а для локального пакета можно явно передать готовый JAR в `agentDocs` с форматом базового пакета.

Документация библиотеки копируется в `.agents/backstage/<group>/<artifact>/`, а её skills — в `.agents/skills/`. Плагин пересчитывает относительные Markdown-ссылки между документацией и skills при установке и создаёт общий `LIBRARIES.md` со ссылками на базовый пакет, библиотеки и их skills. Если пакеты поставляют skill с одинаковым именем, Gradle сообщает об обоих источниках до обновления файлов.

## Подхват инструкций агентом

При применении плагина в корневой `AGENTS.md` приложения автоматически добавляется отдельный блок со ссылкой на документацию. Если файла ещё нет, он будет создан. Пример для стандартного выходного каталога с базовой документацией.

```markdown
<!-- backstage-agent-docs:start -->
## Компоненты Backstage

При работе с подключёнными библиотеками выбери подходящий skill или справочник.

- [Каталог документации](<.agents/backstage/README.md>) содержит ссылки на материалы по модулям.
<!-- backstage-agent-docs:end -->
```

Повторное применение обновляет только текст между маркерами включительно, сохраняя остальные инструкции. При наличии материалов из зависимостей ссылка ведёт на `LIBRARIES.md`. Она строится относительно корневого `AGENTS.md` с учётом `agentDocs.outputDirectory`. Зависимости берутся из проекта, в котором подключён плагин. Ссылка на прежнюю задачу `syncAgentDocs` внутри управляемого блока удаляется.

Не удаляй отдельный маркер и не дублируй управляемый блок: в таком случае конфигурация завершится ошибкой и оставит `AGENTS.md` без изменений. При удалении установленных файлов следующий импорт/запуск Gradle восстановит их, в том числе при использовании configuration cache. Корневой `CODEMAP.md` приложения плагин не изменяет.
